# 知识题卡与岗位场景

整理日期：2026-10-23。题库定义位于 `content/questions.ts`，岗位、公司场景和中文标签位于 `content/profiles.ts`。

## v0.2 自主出题

知识卡是素材与知识依据。AI 场次据此生成新的题干、情境、实际评分标准与参考答案，并保存本场快照。每次回答由模型作语义判断，可创作新的追问；主问题和追问均须引用允许的知识点及资料 ID。固定题干和两条预设追问仍可用于无需模型的题卡练习，不限制 AI 场次的提问文本。

动态题快照的 `generation` 保存知识卡 ID、版本、原始知识要点和来源锚点；生成内容标为 `draft`，不能声称已人工审定。辅导反馈会标记后续同题回答为辅助作答，模拟判断在面后显示。评分须按各轮回答之前实际问过的内容判断，后来的追问不能回溯扩大首答要求。

## 覆盖范围

当前共 36 张题卡，覆盖 12 个领域，每领域 3 张。每张题卡提供简单、中等、困难 3 种题干，共 108 个难度变体，并包含 4 个评分要点、2 条定向追问、提示、常见误区与参考答案。变体属于同一题目家族，不作为 3 道独立知识点计算覆盖率。

| 领域 | 题卡 |
| --- | --- |
| 操作系统 | 进程与线程如何取舍；内存上涨的定位方法；共享资源与死锁 |
| 计算机网络 | 一次 HTTPS 请求经历什么；缓存与内容更新；超时后能否直接重试 |
| 数据库 | 索引选择与查询计划；并发更新与事务边界；关系建模与数据约束 |
| 前端工程 | 组件状态与派生数据；搜索请求的乱序响应；可操作的弹窗与表单 |
| 后端工程 | API 的边界与权限；后台任务与重复执行；翻页接口的稳定性 |
| 系统设计 | 短链接服务的最小设计；缓存一致性与热点；文件上传的完整链路 |

| 编程语言 | 资源所有权与生命周期；异步与并发限制；错误处理与抽象边界 |

岗位包含后端、前端、全栈、平台与基础设施、C / C++、AI 应用与 Agent。题目通过 `roles` 标记适用岗位；同一领域的题目并非对所有岗位都适用。

公司配置包含通用岗位、两个明确标记为虚构的业务场景，以及用户输入公司名称和 JD 的自定义配置。知阶学习、云栈科技都是原创模拟设定，不代表真实公司的业务、招聘要求或面试风格。自定义 JD 是用户提供的上下文，不能自动变成已核实公司事实。

## 题目来源与核对程度

全部题卡的 `origin` 为 `generated`：题干、情境与评分结构由本项目原创整理。没有整段导入开源题库，没有将生成题标记为某家公司真题。`review: assistant_checked` 表示助手整理并检查过要点与字段引用，**不代表人类专家完成核验，也不代表经过真实候选人评分校准**。

技术卡的 `sources` 用于核查概念和进一步阅读。参考答案是一种合理回答路径，题卡要点允许其他正确实现和不同技术栈，不应要求逐字复述。涉及数据库隔离、取消机制与部署行为时，需要候选人说明具体产品或语言及适用条件。

项目、行为以及 Agent 评估题的评分结构是本项目的练习设计，其 `sources` 可以为空；这些要点应与候选人的具体回答交叉核对，不应伪装成已有行业测量标准。真实经历和假设场景须清楚区分，假设回答可以讨论方法，但不能证明实际履历。

题目组织参考以下项目，没有复制其题干、代码或答案：

- [Tech Interview Handbook](https://github.com/yangshun/tech-interview-handbook)：算法与面试准备主题。
- [System Design Primer](https://github.com/donnemartin/system-design-primer)：系统设计问题的拆解维度。
- [Developer Roadmap](https://github.com/nilbuild/developer-roadmap)：跨岗位知识范围的组织参考。

技术核对主要使用题卡内对应的一手资料，例如 [PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[MDN HTTP 缓存](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)、[React 状态与 Effect](https://react.dev/learn/you-might-not-need-an-effect)、[Kubernetes 探针](https://kubernetes.io/docs/concepts/workloads/pods/probes/)、[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-raii) 和 [Anthropic Agent 工程](https://www.anthropic.com/research/building-effective-agents)。完整链接保留在各卡片，便于独立核对。

## 难度与评价边界

- 每个难度变体通过 `expectedPointIds` 显式指定题干实际要求的要点，不能按难度机械要求答完四项。未问到的内容不能作为缺失项扣分。
- 例如进程与线程题的中等档要求选择依据，不强制回答困难档的崩溃恢复；锁题的简单档只要求解释共享计数竞争和处理方法；缓存题的困难档聚焦共享缓存边界，不要求顺带讲完静态资源版本管理。
- 中等题增加具体应用与验证；困难题增加失败、约束和取舍，仍按目标岗位级别讨论。
- 同一卡片的高难度情境可能改变问题重点，因此各档必答要点不必形成数量递增的包含关系。通用参考答案覆盖题卡整体，判分仍以当前题干及其显式要点为准，其他正确回答路径应接受。
- 追问通过 `targetPointIds` 关联要点，不应在模拟模式中直接展示提示或参考答案。
- 项目贡献只按用户明确提供的经历和证据评价，不能根据简历中的项目名称推定掌握程度。
- 算法题目前支持文字解释、伪代码与复杂度讨论，题库本身不包含运行代码的判题沙箱。
- 固定题卡模式每卡只有两条已写定追问；AI 模式按实际回答生成新追问，简单、中等、困难分别最多 1、2、4 次，并可提前换题。

## 数据检查

数据完整性检查覆盖：36 个题目 ID 唯一、每个领域恰好 3 张、所有难度与追问引用的评分要点存在、题目的岗位 ID 有对应配置、每个岗位配置领域均至少有一道适配题。尚未完成专家评分校准或真人练习效果研究。

后续新增题卡时，应保留唯一 `id` 和家族标识，明确原创、改编或面经报告的来源性质，再填写各档题干、评分要点和定向追问。真实公司资料应另行记录来源、日期与不确定性，不借用虚构场景替代真实公司调研。
