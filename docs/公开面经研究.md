## 写入应用的行为模式

以下是本项目基于上述记录形成的设计建议，不是原帖的标准答案或对公司风格的统计结论。

| 模式 ID | 应用方式 | 主要依据 |
| --- | --- | --- |
| `project-request-chain` | 从一项操作追输入输出、上下游与本人负责部分 | E01、E07 |
| `resume-claim-to-code` | 对主动声称的能力追实现证据，允许澄清贡献边界 | E04、E05 |
| `frontend-observable-interaction` | 解释后讨论输出或状态，再改变一个交互条件 | E03、E04 |
| `backend-component-boundary` | 从实际采用的组件追选择依据与一个失败窗口 | E01、E07 |
| `cpp-mechanism-to-execution` | 从机制进入小范围实现、边界与测量条件 | E02 |
| `algorithm-explain-and-vary` | 先核对思路，再作单一条件变化，记录提示使用 | E01、E02 |
| `agent-one-request-lifecycle` | 沿一条请求追检索、工具、记忆及异常状态 | E05、E06 |
| `bounded-adaptive-interview` | 根据回答调整分支与时间，保持尊重并允许不会 | E01、E03、E05 |
| `collaboration-evidence` | 从分歧或受挫事件追行动、决定依据和后续 | E07 |

模块将这些模式关联到现有岗位 ID 和 `Topic`。适用于所有岗位的通用追问是本项目的迁移设计；本次没有获得足够可读的平台 / SRE 第一人称材料，因此不宣称已研究平台岗位的专属面试流程。

## 接入与使用边界

1. 按当前岗位与题目主题选择少量相关模式。每次提问仍围绕当前回答的一个缺口，不能把多条行为规则拼成一串审问。
2. 当前题干、难度和 `expectedPointIds` 决定必答范围；面经模式不能额外增加评分必答项，也不能从其中抽取技术答案作为真值。
3. 候选人没有相关经历时，允许缩小范围或转为标明的假设讨论。项目真实性核对依靠具体证据，不使用冒犯或诱导性的断言。
4. 简单、中等、困难控制追问深度与条件复杂度；不仿照文章中的强度给所有人同样题量，也不凭“第几面”自动推定难度。
5. 保留来源和日期缺口，不生成“某公司必考”“出现概率”“按这种回答必过”等结论。7 篇材料是有目的选择的小样本，不能用于频率排名。

## 排除情况与验证

检索出现过批量“真题含完整答案”汇编、未能回到原帖的二次整理，以及只返回页面导航的帖子。它们未计入这 7 篇样本；搜索摘要和推荐栏内容也未代替正文。网页正文中的候选人回答没有被作为技术正确性依据。

提问策略只影响出题和追问方式。技术判断仍以知识卡与实际问答为依据，公司资料也不会从个人面经自动写入。
